# How-To: Wazuh vulnerability dashboard (Greenbone)

> **Summary.** A native OpenSearch Dashboards view of Greenbone findings over `wazuh-alerts-*`, filtered to `rule.groups: greenbone`. Live and interactive, complementing the point-in-time SVG dashboard (`docs/vuln-dashboard.*`). The saved-objects NDJSON is generated by `scripts/wazuh_dashboard_gen.py` and version-controlled in this repo.

## What it shows

Panels over `wazuh-alerts-*`, query `rule.groups: greenbone`:

- Total Greenbone alerts (KPI)
- Severity tier donut on `rule.level` (2=Low, 5=Medium, 10=High, 12=Critical)
- Threat band bar on `data.threat`
- Top vulnerable hosts on `data.host`
- Top findings on `data.name`
- Top CVEs on `data.cves`
- By scan on `data.task`
- Remediation posture on `data.solution_type`
- Alert timeline (date histogram split by `rule.level`)

## Field facts (verified via wazuh-logtest on real findings)

The pipeline appends the collector's raw JSON to the manager localfile
`/var/ossec/logs/greenbone/findings.jsonl`; Wazuh's **built-in `json` decoder**
extracts every field, so these are indexed under `data.*`:

`data.host`, `data.name`, `data.threat`, `data.severity` (string, e.g. `7.500000`),
`data.family`, `data.task`, `data.solution_type`, `data.cves` (array), `data.nvt_oid`,
`data.vuln_port`, `data.qod`, plus `rule.id`, `rule.level`, `rule.groups`.

Severity tiers map to `rule.level`, which is always a numeric field:
Low->2, Medium->5, High->10, Critical->12. The dashboard buckets on `rule.level`
rather than the string `data.severity`, so no scripted/numeric field is required.

### PITFALL: data.port is a RESERVED object mapping — do NOT emit a string `port`

The `wazuh-alerts-*` index template maps `data.port` as an **object** (other Wazuh
modules nest fields under it). Greenbone's port is a scalar string
(`"general/tcp"`, `"package"`, `"53/udp"`). If the collector emits `port` as a
string, analysisd still generates the alert (visible in `alerts.json`), but the
**indexer rejects the whole document** with:

```
mapper_parsing_exception: object mapping for [data.port] tried to parse field [port]
as object, but found a concrete value
```

Symptom: `alerts.json` shows N greenbone alerts, but `wazuh-alerts-*` shows ~0.
Every real finding silently fails to index while UniFi and other sources index fine.
**Fix (applied):** the collector emits the scanned port as **`vuln_port`**, not
`port`. Keep it that way for any new source that carries a port. To detect the
class of bug, test-index one real alert doc straight into the index and read the
error, rather than trusting the alert count.

**Dependency:** the `data.host/name/task/family/solution_type/vuln_port` fields
appear in the index mapping only once REAL findings are indexed. Until a pull is
ingested, those panels show "No results". `data.severity`, `data.threat`,
`rule.level`, `rule.groups` are already mapped.

### PITFALL: dashboard panels must fill the 48-column grid

OpenSearch Dashboards lays panels out on a **48-column responsive grid**. The grid
rescales to the browser window, so panels always resize proportionally, but a panel
placed at width 24 (half the grid) alone in a row leaves the **right half of that row
empty**. The symptom looks like "the graphs aren't autofitting to the window" when it
is really unused grid space.

Rule: **every row's panel widths must sum to 48.** `scripts/wazuh_dashboard_gen.py`
enforces this with an `assert` on each row. Current layout:

| Row | Panels (width) | Sum |
|-----|----------------|-----|
| 1 | KPI (12) + Severity tier (12) + Threat band (24) | 48 |
| 2 | Top hosts (24) + Top findings (24) | 48 |
| 3 | Top CVEs (24) + By scan (24) | 48 |
| 4 | Remediation posture (48) | 48 |
| 5 | Alert timeline (48) | 48 |

To reshape, edit the `rows` list in `build_dashboard()` (keep each row summing to
48), regenerate, and re-import with `overwrite=true`.

## Generate the NDJSON

```bash
# index-pattern id for wazuh-alerts-* (usually the title itself on this build)
python3 scripts/wazuh_dashboard_gen.py \
  --index-pattern-id 'wazuh-alerts-*' \
  --out docs/wazuh-vuln-dashboard.ndjson
```

Deterministic: same inputs -> same NDJSON, so it diffs cleanly in git.

## Import into the Wazuh dashboard

UI: **Dashboard management -> Saved objects -> Import**, choose the NDJSON,
"Automatically overwrite conflicts".

API (read `WAZUH_IDX_USER`/`WAZUH_IDX_PASS` from env; dashboard on :443):

```bash
curl -sk -u "$WAZUH_IDX_USER:$WAZUH_IDX_PASS" -H 'osd-xsrf: true' \
  -X POST "https://<WAZUH_HOST>/api/saved_objects/_import?overwrite=true" \
  --form file=@docs/wazuh-vuln-dashboard.ndjson
```

`{"success":true,"successCount":10}` = imported. Open the dashboard
"SOC Pipeline - Vulnerability (Greenbone)".

## Rollback

Delete the imported objects (dashboard id `soc-pipeline-vuln-greenbone` + the
`vuln_*` visualization ids) via Saved Objects, or:

```bash
for id in soc-pipeline-vuln-greenbone vuln_kpi_total vuln_sev_tier vuln_threat \
  vuln_top_hosts vuln_top_findings vuln_top_cves vuln_by_scan vuln_solution vuln_timeline; do
  curl -sk -u "$WAZUH_IDX_USER:$WAZUH_IDX_PASS" -H 'osd-xsrf: true' \
    -X DELETE "https://<WAZUH_HOST>/api/saved_objects/${id%% *}/$id" ; done
```

Import creates only NEW saved objects; it does not alter the index, other
dashboards, or any rule.

## Re-populating the index (why the dashboard may look empty)

Wazuh tracks the read offset of `findings.jsonl` and `run_pipeline.py` dedupes on
`report_id+nvt_oid+host`, so a fresh scan's already-seen findings won't re-alert,
and past alerts age out of `wazuh-alerts-*`. To deliberately repopulate for a demo
or after an index rotation, reset the delivered-state file and re-append the current
findings (a change-controlled live action: back up first, verify read-back). See the
action log entry for the approved procedure.

## Automated feed (cron)

The data feed is automated so the dashboard stays current without a manual pull.

- **Wrapper:** `scripts/greenbone-pull.sh` (source of truth in this repo;
  installed to `/opt/soc/scripts/` where the Hermes scheduler runs it). It opens a
  read-only SSH socket-forward to gvmd, runs `run_pipeline.py`, and tears the forward
  down via a trap. Dry-run: `GB_DRYRUN=1 /opt/soc/scripts/greenbone-pull.sh`.
- **Schedule:** Hermes cron job `986f789422a3` ("Greenbone weekly vuln pull ->
  Wazuh/Graylog"), `0 7 * * 6` (Sat 07:00 UTC, just after the weekly scan window
  which ends ~06:00 UTC). `no_agent` script job (no LLM), `deliver=local`.
- **Runs on:** the Hermes agent host (owns the SSH keys, `.env` creds, python-gvm
  venv, and pipeline code). The scanner and Wazuh manager only receive.
- **Idempotent:** dedupe on `report_id+nvt_oid+host` means a run delivers 0 unless
  Greenbone produced a genuinely new report; no duplicate alerts.
- **Status:** one-line JSON per run appended to `/var/log/greenbone-pull.log`;
  job history via `cronjob list` (last_status/last_run_at). Local-only, so no message
  is pushed anywhere; check the log or job status on demand.

Note: the dashboard VIEW is always live (re-aggregates the index on open/refresh);
this cron only keeps the underlying DATA fresh.
